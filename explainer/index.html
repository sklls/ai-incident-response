how the library is built

One commander, four tiers

The library isn't a pile of prompts. It's a chain of command: an orchestrator that runs the lifecycle, a specialist it consults for each kind of failure, and shared governance parts every step relies on.

tier 0 · boss incident-commander
tier 1 · lifecycle triagecontaininvestigate remediatecommunicatepost-mortem
tier 2 · specialists privacy-breachfairness-biasagent-autonomy
tier 3 · governance severity-matrixapproval-gateaudit-ledgerregulatory-map
▸ commander calls triage → consults a specialist → scores with severity-matrix
▸ reaches a consequential step → opens approval-gate → waits
▸ every action → written to audit-ledger (append-only, tamper-evident)
▸ before any notice → regulatory-map sets the obligations & deadlines

Each skill does one job, so you can read it, trust it, and reuse it across every scenario. The lifecycle (tier 1) is the shared spine; the specialist (tier 2) changes what is detected and how you contain; the governance parts (tier 3) make oversight consistent instead of improvised.

The design is traceable on purpose: every skill is headed by the framework it enforces — EY's agent guardrails, NIST, the four-fifths rule, India's DPDP Act & IT Act §11, ISO/IEC 42001. The library is the governance framework, made runnable.

the one rule that matters

The agent can propose. Only a person approves.

Before anything consequential — shutting a system down, deploying a fix, sending a notice — the agent stops and asks. And it only believes the answer if it's written down.

Incident opened — severity set S1
Agent proposes: freeze outbound payments
awaiting human approval
Freeze outbound payments · blast radius: all · Sev S1
ApproveReject
Human approves — recorded in the ledger
Agent re-reads the record, then acts

A click in a browser can't nudge the agent along. So the agent writes the request, pauses its turn, and only continues once it reads an approved record in the database — not a spoken "go ahead".

if the record says pending → it refuses and waits.
if it says rejected → it holds, and proposes another way.
no record, no action.

Every outcome — approve, reject, or still-waiting — and who decided it, lands permanently in the audit trail. That's what makes oversight provable instead of remembered.

same spine, three failures

One lifecycle, three shapes of "stop it"

The steps never change. The specialist changes what gets detected, how you contain, and which law applies — and containment looks different every time.

S1 · privacy

Chatbot leaks another customer's data

contain by: shutting it down
  • scope it: one conversation, or many?
  • cause: cache served across sessions
  • clocks: CERT-In 6h · DPDP 72h
S2 · fairness

Hiring tool rejects one group more

contain by: routing to human review
  • test: four-fifths and significance
  • cause: a proxy feature for a protected trait
  • law: Art. 14/15 · NITI · (EEOC)
S1 · autonomy

Finance agent pays beyond its limit

contain by: revoking its authority
  • cause: prompt injection in an invoice field
  • fix: a hard limit outside the model
  • law: IT Act §11 · RBI FREE-AI
